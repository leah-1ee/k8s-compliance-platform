# TASK-13: Grafana OSS Multi-Tenant Observability

## Goal

사용자가 로그인한 뒤 자기 클러스터 관측 데이터를 Grafana 대시보드 형태로 볼 수 있게 하되, Grafana OSS 환경에서 다른 사용자/데모 클러스터 데이터가 노출되지 않도록 격리한다.

현재 판단:

- 단순 Grafana URL 변수(`var-cluster=...`)는 보안 격리가 아니다.
- Grafana OSS의 folder/org 권한은 대시보드 접근 격리에는 유용하지만, 단일 Prometheus datasource가 모든 데이터를 조회할 수 있으면 데이터 격리가 완전하지 않다.
- 현실적인 OSS 설계는 **Grafana org/folder 분리 + KubeOwl Prometheus 프록시** 조합이다.

## Target Design

1. Grafana OSS는 사용자별 org 또는 folder를 분리해 대시보드 접근을 나눈다.
2. Grafana datasource는 Prometheus를 직접 보지 않고 KubeOwl backend proxy를 바라본다.
3. KubeOwl proxy는 JWT/session/user ownership을 확인한 뒤 사용자 소유 `cluster_id`만 PromQL에 강제 주입한다.
4. Prometheus는 ClusterIP + NetworkPolicy로 클러스터 내부에서만 접근 가능하게 둔다.
5. 사용자는 KubeOwl UI에서 자기 Grafana org/folder dashboard로 이동한다.

## Security Requirements

- Prometheus는 외부에 노출하지 않는다.
  - NodePort/LoadBalancer 금지
  - ClusterIP only
  - NetworkPolicy로 ai-server/proxy pod에서만 ingress 허용
- Grafana datasource URL은 Prometheus가 아니라 KubeOwl proxy여야 한다.
- PromQL 필터링은 정규식 치환으로 처리하지 않는다.
  - PromQL parser 또는 안전한 AST 기반/문법 기반 주입을 사용한다.
  - 모든 metric selector에 `cluster_id="<owned-cluster-id>"`를 강제 주입한다.
  - 클라이언트 query에 기존 `cluster_id`가 있어도 신뢰하지 않고 override한다.
- 모든 proxy 요청은 감사 로그를 남긴다.
  - `timestamp`, `user_id`, `cluster_id`, `path`, `original_query`, `injected_query`, `status_code`
- proxy는 사용자 기준 rate limit을 둔다.
  - 초기값: 60 requests/minute/user

## Implementation Plan

### 1. Kubernetes manifests

대상 namespace: `monitoring`

- Prometheus PVC
  - `local-path`, `5Gi`, `ReadWriteOnce`
- Grafana PVC
  - `local-path`, `2Gi`, `ReadWriteOnce`
- Prometheus Deployment/Service
  - `prom/prometheus:latest`
  - Service: ClusterIP only
  - PVC mount: `/prometheus`
  - retention: `7d`
- Grafana Deployment/Service
  - `grafana/grafana:latest`
  - Service: NodePort only for Grafana
  - PVC mount: `/var/lib/grafana`
  - admin credentials from Secret
- NetworkPolicy
  - deny all ingress to `app=prometheus`
  - allow ingress only from `app=ai-server` or dedicated proxy label

### 2. Grafana provisioning

Add module:

- `ai-observability/ai-server/app/grafana/provisioning.py`

Behavior:

- `provision_user(user_id, cluster_id, email)` must be idempotent.
- Check local SQLite mapping first.
- Create Grafana org named `org-{user_id}` or user folder depending on final UX choice.
- Create datasource in that org:
  - type: `prometheus`
  - url: `http://ai-server/grafana/prometheus/{cluster_id}`
  - access: `proxy`
  - default: true
- Import master dashboard JSON with datasource UID replacement.
- Add user as Viewer.
- Save mapping to SQLite.
- On failure, rollback created Grafana org/resources and raise `ProvisioningError`.

### 3. Prometheus proxy

Add modules:

- `ai-observability/ai-server/app/grafana/proxy.py`
- `ai-observability/ai-server/app/grafana/promql_inject.py`

Mount:

- `/grafana/prometheus/{cluster_id}/{path:path}`

Support endpoints:

- `GET/POST /api/v1/query`
- `GET/POST /api/v1/query_range`
- `GET /api/v1/series`
- `GET /api/v1/labels`
- `GET /api/v1/label/{name}/values`
- `GET /api/v1/metadata`

Request flow:

1. Verify JWT/session.
2. Confirm requested `cluster_id` belongs to current `user_id`.
3. Apply per-user rate limit.
4. Extract PromQL query/match parameters.
5. Inject/override `cluster_id`.
6. Write audit log to stdout and file.
7. Forward request to internal Prometheus.
8. Return Prometheus response as-is.

### 4. PromQL injection tests

Add tests:

- bare metric: `up` -> `up{cluster_id="abc"}`
- metric with labels: `http_requests_total{method="GET"}` -> add `cluster_id`
- existing cluster label: `up{cluster_id="evil"}` -> override to `abc`
- binary expression: `up + http_requests_total`
- subquery/function: `rate(http_requests_total[5m])`
- aggregation: `sum by (pod)(metric)`
- empty query raises `ValueError`

### 5. Proxy auth tests

Add tests:

- valid JWT/session + matching cluster ownership -> 200
- mismatched path `cluster_id` -> 403
- cluster not owned by user -> 403
- missing/invalid/expired token -> 401
- rate limit exceeded -> 429 with `Retry-After`

## Open Decisions

- Use Grafana org per user or folder per user?
  - Org gives clearer resource separation.
  - Folder is lighter but weaker for datasource isolation.
  - Initial recommendation: org per user for ~10 users.
- Use app session cookie or short-lived JWT for Grafana datasource proxy?
  - Grafana datasource requests may not carry KubeOwl browser session cleanly.
  - Initial recommendation: short-lived signed token generated by ai-server for Grafana datasource/proxy usage.
- Whether dashboards should be embedded in KubeOwl UI or opened in Grafana.
  - Initial recommendation: open Grafana org dashboard in a new tab after provisioning.

## Non-Goals

- Do not rely on Grafana Enterprise datasource permissions.
- Do not expose Prometheus directly.
- Do not implement URL-variable-only isolation.
- Do not store or expose user cluster tokens in Grafana.

## Validation

Local:

```bash
.venv/bin/python -m pytest ai-observability/ai-server/tests/
node --check ai-observability/ai-server/app/static/app.js
```

VM smoke:

1. New Google user logs in.
2. User registers cluster.
3. Grafana provisioning creates user org/folder and datasource.
4. User dashboard shows only that cluster.
5. Attempt to query another `cluster_id` through proxy returns 403 or overridden query returns no cross-tenant data.
6. Prometheus has no external service.
7. NetworkPolicy blocks non-proxy ingress to Prometheus.
